QMux

QMux

Overview

QMux is a Go framework that runs independent application protocols over DNS. Each protocol owns a (QCLASS, QTYPE) pair, and the QNAME identifies the resource. A developer registers a handler for a protocol key. QMux does all DNS packet processing, the envelope encoding, and the signatures.

QMux has three parts. The library is importable: an authoritative server, a client SDK, a protocol registry, a CBOR envelope codec, discovery, and Ed25519 signing. The three command-line tools are qmuxd, qmuxctl and qmux-probe. The research harness holds an embedded-device recovery demonstration, a resolver interop matrix, and benchmarks against IN-class DNS, CoAP and HTTPS.

The project exists to answer one research question. The user stated it as follows:

"The central research question is whether multiple DNS classes provide a measurable benefit for application protocol multiplexing compared with conventional IN-class DNS. Design the implementation so that this question can be answered objectively."

Every design choice below keeps that question measurable. The class is the only variable between the private-class path and the IN-class baseline. The payload bytes, the signatures and the server code are the same on both paths.

QMux is not a DNS tunnel. It is not a replacement for conventional DNS. It is not a TCP-over-DNS transport. The source brief is the user's pasted "QMux — Implementation Specification" (2026-11-20). This spec restates it and adds the decisions from the planning interview.

Goals

  1. Two or more protocols answer through independent private classes on one authoritative

server, over UDP and over TCP.

  1. A client discovers the protocols of a server, negotiates a protocol version, and queries

each protocol with no hard-coded class numbers other than the discovery key.

  1. Every answer RR carries a deterministic CBOR envelope, and the client decodes it strictly.
  2. A client with trust anchors rejects each tampered, expired, replayed, mis-bound or

unsigned envelope, and reports the reason.

  1. The embedded demonstration reconciles a stale device end to end with one command.
  2. The interop matrix is reproducible with one command on any host with Docker, and CI runs it.
  3. The benchmark measures QMux private classes against IN + private type, IN + TXT, CoAP and

HTTPS with equal payloads. The results separate measured values from assumptions.

  1. go test ./..., go test -race ./..., go vet ./... and the linter pass on every batch PR.
  2. The library module depends on two third-party modules only: miekg/dns and fxamacker/cbor.

Non-goals

  • DNS tunnels, payload fragmentation, or DNS-based file transfer.
  • Recursive resolution, delegation, zone transfer, DNSSEC signing, or dynamic update.
  • A DNS management platform, a web frontend, a database, or Kubernetes.
  • State-changing operations: remote command execution, arbitrary RPC, device control.
  • Firmware flashing in the demonstration.
  • Public-resolver compatibility claims. QMux tests BIND and Unbound only.
  • Confidentiality. DNS carries the envelope in clear text. Signatures give integrity and

origin authentication only.

  • A packaged release, a container registry push, or a hosted deployment in v1.
  • An EDNS option that carries the protocol version. Version 1 uses the version label only.
  • Private-class resolution through Unbound with custom root hints.

Two Go modules exist:

  • The library module github.com/Crank-Git/qmux at the repository root holds pkg/,

cmd/, examples/ and tests/integration/.

  • The harness module at tests/interoperability/ holds the baselines and qmux-bench.

QMux has no deploy target. Nothing runs in production. CI is the only automated environment.

Envelope (RDATA of every answer RR, from Epic 4)

A CBOR map with unsigned integer keys, encoded with cbor.CoreDetEncOptions().

KeyFieldCBOR typeConstraint
0formatuintMust be 1.
1protocol IDtext1–128 bytes, reverse-DNS form, lowercase [a-z0-9.-].
2protocol versionuint1–65535.
3message typeuint1 = record, 2 = manifest. 256–65535 are protocol-specific.
4application statusuintSee the status table.
5payloadbytesLength 0 to the payload limit.
6signature blockmapOptional on the wire. Required when the client has trust anchors.

Envelope limits: the envelope is at most 16384 bytes by default. The configured maximum is never above 65000 bytes. The decoder rejects unknown keys, duplicate keys, indefinite lengths, tags, invalid UTF-8, and nesting deeper than 8 levels.

Application status:

ValueNameMeaning
0okThe payload holds the requested resource.
1not-foundThe protocol has no resource for the QNAME.
2bad-requestThe QNAME labels do not parse for this protocol.
3version-unsupportedThe version label names a version the registration does not support.
4unavailableThe handler cannot answer now.
256–65535protocol-specificThe protocol defines the meaning.

Signature block (envelope key 6, from Epic 6)

KeyFieldCBOR typeConstraint
1key IDbytesExactly 8 bytes.
2algorithmint-8 (EdDSA, RFC 9053). Other values are rejected.
3issued_atuintUnix seconds.
4expires_atuintUnix seconds. Greater than issued_at.
5signaturebytesExactly 64 bytes.

The signing input is the deterministic CBOR encoding of this array:

["qmux-sig/1", qname, qclass, qtype, format, protocol_id, version,
 message_type, status, payload, key_id, alg, issued_at, expires_at]

qname is the lowercase fully qualified QNAME. The signature binds the resource name, the class, the type and the protocol ID. A valid envelope copied to another QNAME or another protocol key fails verification.

Cross-cutting concerns

Protocol key allocation

  • The registry accepts private classes 65280–65534 and IN (1).
  • The registry accepts a reserved class only when AllowReservedClasses is true.
  • The registry rejects every other class, for example 0, 254 (NONE) and 255 (ANY).
  • The registry accepts private types 65280–65534.
  • The registry accepts a non-private type only when AllowNonPrivateTypes is true. That

option exists for the TXT reference row of the benchmark and probe.

  • The registry always rejects the types 0, OPT (41), TSIG (250), IXFR (251), AXFR (252),

ANY (255) and the reserved type 65535.

  • Class and type numbers are local to one server. A protocol ID is the stable name. The

manifest maps protocol IDs to protocol keys.

Error semantics

The RCODE reports DNS-level outcomes. The application status reports application outcomes. They never overlap.

ConditionRCODEAnswer
A registration answers, with any application statusNOERROR, AA setOne RR with the envelope
The question count is not 1, or the packet does not parseFORMERRnone
The opcode is not QUERYNOTIMPnone
No registration for the protocol keyREFUSEDnone
The QNAME is outside every configured zoneREFUSEDnone
The source exceeds its rate limitREFUSEDnone
The handler returns an error, times out, or the envelope exceeds limitsSERVFAILnone
The EDNS version is above 0BADVERSnone

The client returns three separate Go error types:

  • *client.DNSError for an RCODE that is not NOERROR, a transport failure, a timeout,

or a mismatch between the question and the answer.

  • *client.AppError for an application status that is not ok.
  • *client.VerifyError for a signature or freshness failure.

Security posture

  • DNS gives no confidentiality, no integrity and no authentication. QMux assumes an

on-path attacker can read, drop, replay and forge packets.

  • A client with trust anchors verifies every envelope before it returns any field.
  • A client with trust anchors never returns an unsigned or unverifiable envelope. No

silent fallback exists.

  • A client with no trust anchors returns results with Verified: false. Discovery

refuses to run without trust anchors unless the caller sets InsecureSkipVerify.

  • The TTL is never a security expiry. Only expires_at is.
  • QMux supports read-only operations only.
  • The server enforces a maximum query size of 512 bytes without EDNS(0) and 1232 bytes

with it. It enforces the envelope limit and an optional per-source rate limit.

  • Fuzz tests cover the envelope decoder, the server request path and the verifier.

Logging

The server and qmuxd log with log/slog. One record per query carries qname, qclass, qtype, transport, source, rcode, status, bytes_in, bytes_out and duration_ms. The default level is info. The library never logs payload bytes or private keys.

Performance targets

  • A direct UDP query on loopback completes in under 2 ms at the median. This is a

target, not a claim. The benchmark measures it.

  • A normal response fits in 1232 bytes, so it travels over UDP with no truncation.
  • The server handles 100 concurrent queries with no data race under go test -race.

Environments & config

EnvironmentPurpose
LocalA developer runs make test, make interop, make bench and the demonstration.
CIGitHub Actions runs the test, race, vet and lint jobs on every PR to dev and main. A second workflow runs the interop matrix.

QMux reads no environment variables. Every setting is a Go config struct field or a command-line flag. qmuxd reads its configuration file from --config.

Secrets:

  • Signing keys are generated with qmuxctl keygen and are never committed.
  • .gitignore excludes *.key.
  • Tests derive keys from fixed seeds in test code with ed25519.NewKeyFromSeed.
  • The demonstration generates a fresh key at each start.

Seed data:

  • examples/qmuxd.json is a working configuration file for the three demonstration

protocols.

  • tests/interoperability/qmuxd.json is the probe configuration.

Assumptions

  1. The module path is github.com/Crank-Git/qmux, and the license is MIT.
  2. A root package qmux holds type aliases and constructors, so the brief's API examples

compile without change. The real code lives in pkg/. See ADR 0004.

  1. pkg/transport is the DNS wire layer and the only importer of miekg/dns.
  2. Discovery uses the protocol key (65280, 65534) and the discovery name _qmux.<zone>.

The IN option uses (1, 65534) with the same discovery name.

  1. A request names its protocol version with an optional leftmost QNAME label _v<N>. With no

version label, the server uses the highest version of the registration. A QNAME label passes through every resolver, but an EDNS option can be stripped.

  1. The authoritative server signs each envelope at answer time (online signing). Handlers

never sign.

  1. Replay protection uses the validity window plus a monotonic issued_at check per

protocol ID and QNAME in the freshness store. QMux uses no nonces, because a DNS question carries no client nonce through a resolver cache.

  1. The decoder enforces deterministic encoding for signed data: it decodes the envelope,

encodes it again, and compares the bytes. fxamacker/cbor has no decode option that rejects non-deterministic input.

  1. The IN-class baseline uses QCLASS IN, QTYPE 65280, and a protocol label in the QNAME

(_fw.device42.fleet.example.). The class is then the only variable.

  1. The IN + TXT reference row splits the same envelope bytes into TXT character-strings

of at most 255 bytes. QMux protocols never use TXT.

  1. Each benchmark lookup is cold: a new UDP socket, TCP connection or TLS session. HTTPS

with connection reuse is a second, labeled row.

  1. Rate limiting is a per-source-IP token bucket written in QMux. The library default is

off. The qmuxd default is 50 queries per second with a burst of 100.

  1. Version 1 has no release process. Promotion of dev to main is the release.

Risks & open questions

  • Resolvers drop private classes (measured risk, not blocking). BIND 9.20 disables

recursion for every non-IN view (server.c, bind-9.20 branch). A planner test on 2026-11-20 confirmed it: BIND loads a class-65281 view, logs recursion will be disabled for non-IN view 'priv', and answers a class-65281 query with NOTIMP. Unbound 1.26.2 documents "Class IN is assumed" for stub-zone and forward-zone. Private-class probes through both resolvers will most likely fail. The interop matrix records the result. The docs state it as a finding. Only direct queries can carry private classes. Sources:

  • https://gitlab.isc.org/isc-projects/bind9 (bind-9.20)
    • https://github.com/NLnetLabs/unbound (release-1.26.2)
    • https://unbound.docs.nlnetlabs.nl/en/latest/manpages/unbound.conf.html
  • The BIND image is amd64 only. On an arm64 host it runs under emulation, so its

latency is not comparable. Each probe record labels the architecture. The CI run on amd64 is the reference run. The benchmark does not use BIND.

  • Unbound serves expired answers by default (serve-expired: yes in the image). The

interop configuration sets serve-expired: no.

  • DNSSEC validation in the resolvers. Both resolvers validate by default. The

interop configuration marks fleet.example. as insecure (domain-insecure in Unbound, validate-except in BIND), so validation does not hide the class result.

  • miekg/dns v1 is in maintenance mode. It gets fixes only and will be archived. ADR 0001

confines it to pkg/transport.

  • netem needs NET_ADMIN. Docker Desktop on macOS supports it inside its Linux VM.

A host that refuses the capability cannot run make bench. The benchmark then exits with a clear error.

  • Retry timers are a confound in the benchmark. The go-coap defaults (2 s, factor 1.5)

differ from the DNS client (1 s). The user chose equal timers for DNS and CoAP. HTTPS uses the Linux TCP defaults, and the results record them.

No open question remains. Two items moved to the non-goals: an EDNS option for the protocol version, and Unbound root hints for a private class.
